# 结构性变更工作流

## 什么时候调用（触发条件）

**以下任何一种情况，必须先调用本 Skill，按流程走，不能直接动手：**

1. **新增/删除模块或分类** — 侧边栏加新模块、加新分类、删除现有模块/分类
2. **重组导航结构** — 把某个分类从一个模块移到另一个模块
3. **改变信息架构** — 页面从 Tab 改成按钮、从列表改成卡片、新增/删除主要 Tab
4. **新增主要功能入口** — 页面新增一个按钮/链接，跳转到新功能或改变现有功能路径
5. **删除主要功能入口** — 移除已有的功能按钮/入口
6. **改变功能入口位置** — 主要按钮从顶部移到底部、从显眼处移入折叠区等
7. **重构现有面板结构** — 为了更干净/更易维护，重新组织已有内容的结构
8. **改变核心交互方式** — 比如从点击改成拖拽、从弹窗改成内联展开

**以下情况不需要调用（非结构性变更）：**

- 样式调整（颜色、圆角、间距、字体大小、背景色）
- 内容填充（往已有结构里加数据、加知识点、加题目）
- Bug 修复（修复现有功能的错误）
- 文案修改（改标题、改描述文字）
- 辅助功能新增（复制按钮、收起按钮等不影响主路径的小功能）
- 性能优化
- 用户明确说"把XX改成YY"且属于样式/内容范畴

**判断口诀**：如果用户打开工作台，发现"我要找的东西不在原来的位置了"或者"多了一个我没见过的入口"，那就是结构性变更。

## 工作流程（必须按步骤走）

### 第 1 步：判定 + 列方案

我必须输出以下内容，让你确认：

```
### 变更类型判定
- 是否结构性变更：是 / 否
- 判定理由：XXX

### 方案
- 方案 A：[描述方案A，适合什么情况]
  - 改动范围：哪些文件/模块
  - 优点：XXX
  - 缺点/风险：XXX
- 方案 B：[描述方案B，适合什么情况]
  - 改动范围：哪些文件/模块
  - 优点：XXX
  - 缺点/风险：XXX
- 我的推荐：A / B（为什么）

### 完成标准（验收清单）
- [ ] XXX
- [ ] XXX
- [ ] XXX

### 是否涉及修改现有面板
- 是 / 否
- 如果是：为什么不能独立添加？改动范围多大？
```

### 第 2 步：用户确认

你回复"确认"或指定方案后，我才能开始编码。

**没有你的确认，我不写一行代码。**

### 第 3 步：执行

按确认的方案执行。执行中注意：

- 严格按方案范围改，不顺手改其他东西
- 改现有面板时，先确认不会破坏已有功能
- 改完后做基本自测

### 第 4 步：验收

完成后按"完成标准"逐项检查，输出验收结果：

```
### 验收结果
- [x] 完成标准1 — 验证通过（附证据）
- [x] 完成标准2 — 验证通过（附证据）
- [ ] 完成标准3 — 未通过/待确认
```

**涉及 UI/交互的变更，必须附浏览器截图 + 关键交互验证结果。**

### 第 5 步：提交

结构性变更的提交信息必须同时包含两个标记：

```
<type>: <描述> [方案已确认] [验收通过]
```

- `[方案已确认]` — 表示已走完方案确认流程（用户回复过"确认"）
- `[验收通过]` — 表示用户已验收通过

**缺少任一标记，pre-commit hook 会阻止提交。**

## "不修改现有面板"原则

**默认独立添加，嵌入要论证。改现有面板的门槛比新增高。**

| 场景 | 能不能改现有面板 | 处理方式 |
|---|---|---|
| 修 Bug | ✅ 可以直接改 | 修复错误不算"修改" |
| 样式微调（颜色/间距/圆角） | ✅ 可以直接改 | 不影响结构和功能 |
| 新增独立小功能 | ❌ 别动现有面板，独立加 | 能独立就独立，减少影响面 |
| 新功能必须嵌入才能用 | ⚠️ 先讨论再改 | 说明：改哪里、怎么改、为什么不能独立 |
| 重构能减少重复代码 | ⚠️ 先讨论再改 | 说明：当前问题、重构收益、改动范围、风险 |
| 用户明确说"把XX改成YY" | ✅ 按用户要求改 | 你说了算 |

## 禁止开放式提问

**必须用方案对比代替开放式提问。**

| ❌ 开放式提问（禁止） | ✅ 方案对比式（正确） |
|---|---|
| "你觉得怎么做？" | "A 方案简洁但功能少，B 方案功能全但复杂，推荐 A，你选哪个？" |
| "需要我帮你做什么？" | "我可以帮你做 X 或 Y，你需要哪个？还是都要？" |
| "这个你想要什么效果？" | "用红色还是蓝色？红色更醒目蓝色更协调，推荐红色" |
| "你看这样行不行？"（没方案描述） | "方案：XXX，完成标准：YYY，你确认后我开始做" |

**判断口诀**：如果我的问题用户需要"从零开始想答案"，那就是开放式的；如果用户只需要"选 A 还是 B 或者都不要"，那就是方案对比式的。

## 实用优先原则

**不是"能不改就不改"，而是"改之前想清楚值不值"。**

值得改的情况：
- 改完后长期受益（减少维护成本、减少 bug、提升体验）
- 改动范围可控（影响面明确）
- 有明确的问题驱动（现在确实有痛点）
- 用户认可需要改

不值得改的情况：
- 只是"代码看起来更优雅"，用户感知不到
- 改一个地方要动十个文件，风险大
- 只是"预防未来可能有问题"，当前没毛病

**决策方式**：我发现可以优化的地方 → 提出来说明改什么/为什么/改动多大/收益是什么 → 你判断值不值 → 同意就改，不同意就不动。
