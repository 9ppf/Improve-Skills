# 设计稿1:1精确还原工作流

> ⚠️ **重要**：本 Skill 只在用户明确要求"1:1精确还原"时调用。普通的"按设计稿来""大概做成这样"属于「大致对齐档」，直接做就行，不用走这个流程。

## 触发条件

当用户**明确说**以下任一说法时，必须调用本 Skill：

1. **"1:1还原"**、**"一模一样"**、**"逐像素对齐"**、**"精确还原"**
2. **同一个问题改了 2 次还没对**：说明理解有偏差，必须停下来

> 注意：用户说"按设计稿来""大概做成这样""差不多这个意思" → 不属于本 Skill 范围，按「大致对齐档」直接做。

---

## 核心原则

### 三档位原则

| 档位 | 触发条件 | 是否调用本Skill | 做法 |
|---|---|---|---|
| **🔴 1:1精确档** | 用户说"1:1还原""一模一样""逐像素对齐" | ✅ 必须调用 | 列差异清单→用户确认→严格执行 |
| **🟡 大致对齐档（默认）** | 用户说"按设计稿来""大概做成这样" | ❌ 不调用 | 先做一版→用户挑问题→一轮改完 |
| **🟢 创作档** | 用户说"做一个XX""你看着办""好看一点" | ❌ 不调用 | 主动出2-3个方案→用户选→执行 |

**判断方法**：
- 有没有明确目标或参照？没有 → 创作档
- 有参照，但用户有没有说"1:1""精确""一模一样"？说了 → 1:1精确档（调用本Skill），没说 → 大致对齐档
- **默认按大致对齐档执行**，除非用户明确升级

### 严格 ≠ 精确

- **严格**：不改用户没让改的东西、不绕过约束、按约定验证 → 所有档位都要严格
- **精确**：1:1像素级还原、每个细节都对齐 → 只有1:1精确档才需要

## 工作流程

### 第一步：列差异清单（必须）

**改之前必须先列清单，用户确认后才能动手。**

清单格式（表格）：

| # | 改动项 | 设计稿/目标 | 当前状态 | 不改什么（边界） | 优先级 |
|---|---|---|---|---|---|
| 1 | 整体定位卡片 | 紫色左边框+card-label | 长文本+列表 | 内部文字内容不动 | P0 |
| 2 | ... | ... | ... | ... | ... |

**清单必须包含：**
- 改什么（具体到元素和属性）
- 改成什么（具体值或描述）
- **不改什么**（明确边界，防止越界）
- 优先级

### 第二步：用户确认

清单列完后，明确问："以上改动是否确认？确认后我开始改。"

用户回复"确认"/"可以"/"开始"等 → 进入第三步。

### 第三步：逐项修改

- 严格按清单改，**不增不减**
- 改一项勾一项，防止遗漏
- 遇到清单里没覆盖的问题 → 记下来，不私自改，改完统一问
- **同一问题改了2次还没对 → 立即停下来求助**，说明：我理解的需求、我做了什么、结果是什么、我卡在哪了

### 第四步：工作台验证（必须）

**验证必须走完整路径：工作台首页 → 侧边栏点击目标 → iframe 加载 → 检查内容。**

**验证输出必须包含：**
1. 截图（实际页面效果）
2. 关键样式 computed style 对比（设计稿值 vs 实际值）
3. 交互功能验证（折叠、筛选、跳转等）
4. 多页面改动时 → 每个页面逐个验证

**不能只说"已验证"，要有证据。**

### 第五步：用户验收

- 把验证结果给用户看
- 明确问：**"可以提交吗？"**
- 用户说可以 → 提交（提交信息带 `[验收通过]` 标记）
- 用户说有问题 → 回到第三步，按清单补充/修改

## CSS 专项约束

### 强制规则

| 规则 | 说明 |
|---|---|
| **必须用 CSS 变量** | 颜色、间距、圆角、字体大小等设计 token 必须用 `var(--xxx)`，不能硬编码色值 |
| **禁止 `!important` 暴力覆盖** | 除非用户同意，否则用正确的选择器层级解决冲突 |
| **禁止标签选择器全局覆盖** | 不能直接写 `div {}` `p {}` `li {}`，必须带类名限定范围 |
| **禁止通配符 `*` 全局用** | 只能在 reset 里用一次 |
| **类名必须带模块前缀** | 不能裸用 `.card` `.btn` `.item`，必须是 `.zs-card` `.kf-btn` 等 |
| **禁止行内样式覆盖** | 除非是 JS 动态计算的值，静态样式必须写在 CSS 里 |
| **改样式前先查影响范围** | 改一个类之前，grep 确认在哪些文件里用了，影响哪些模块 |
| **改完必须检查相邻元素** | 不能只看改的元素，要看周围布局有没有被影响 |

### 全局样式改动必须先问

以下改动**必须先问用户，确认后才能改**：
- 全局 CSS 变量（`--accent`、`--bg`、`--text` 等）
- 全局标签样式（`body`、`p`、`a`、`li` 等）
- 公共组件样式（`.btn`、`.card`、`.modal` 等）

**问的时候必须说明：**
1. 改了什么（哪些变量/哪些选择器）
2. 从什么值改成什么值
3. 会影响哪些模块

## 内容规范约束

### 知识点必须标注

| 标注 | 说明 |
|---|---|
| **优先级** | 每个知识点必须有"重点/一般/了解"标注 |
| **学习方式** | 每个知识点必须有"理解/记忆/应用/计算"等学习方式标注 |
| **颜色区分** | 优先级必须用颜色做视觉区分，不能只有文字 |

### 标准配色

| 级别 | 颜色 | 色值 | 背景色 |
|---|---|---|---|
| 🔴 重点/最高级 | 红色 | `#ef4444` | `rgba(254, 226, 226, 0.4)` |
| 🟡 一般/中间级 | 黄/橙色 | `#f59e0b` | `rgba(254, 243, 199, 0.3)` |
| 🟢 了解/最低级 | 灰色 | `#6b7280` | `rgba(229, 231, 235, 0.2)` |
| ✅ 正向/已掌握 | 绿色 | `#10b981` | `rgba(209, 250, 229, 0.3)` |
| 🔵 进行中/学习中 | 蓝色 | `#3b82f6` | `rgba(219, 234, 254, 0.3)` |

### 标注格式

统一 badge 形式：`🔴 重点·理解` `🟡 一般·记忆` `🟢 了解·了解`

## 缓存控制约束

| 规则 | 说明 |
|---|---|
| **前端修改必须更新版本号** | 修改 HTML/CSS/JS 后，必须更新模块配置（如 `self-study.json`）中的 `contentUrl` 版本参数 |
| **版本号递增规则** | 小修改 +0.0.1，结构改动 +0.1.0，大版本 +1.0.0 |
| **多页面同步** | 一次改动涉及多个页面，所有页面版本号同步更新 |
| **验证必须强制刷新** | 浏览器验证用 Ctrl+F5 或带版本参数的 URL，不能用缓存页面判断效果 |

## 出错求助机制

**出现以下情况必须立即停下来，向用户求助：**

1. **同一问题改了 2 次还没对** → 说明理解有偏差
2. **浏览器调试 20 分钟没进展** → 不能无限期死磕
3. **发现改动影响范围超出预期** → 需要用户确认是否继续

**求助时必须说明：**
- 我理解的需求是什么
- 我做了什么尝试
- 结果是什么（哪里不对）
- 我需要用户确认什么或提供什么

**不能只说"我做不好"，要说清楚具体卡在哪。**

## 越界界定（1:1精确档下）

| 行为 | 是否越界 |
|---|---|
| 严格按清单修改 | ✅ 不越界 |
| 用户说"改文字颜色"，只改 color 属性 | ✅ 不越界 |
| "顺手"加了背景色、边框、改了圆角 | ❌ 越界 |
| 发现旁边有个小 bug 顺手修了 | ❌ 越界（应该记下来单独提） |
| 觉得"这样更好看"就改了 | ❌ 越界 |
| 清单里没覆盖的问题，先问再改 | ✅ 不越界 |

**核心原则：用户说改什么就改什么，没说的一律不动。**
有优化建议 → 记下来 → 改完后单独提 → 用户确认了再改。
