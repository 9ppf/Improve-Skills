# 文档与版本管理工作流

## 什么时候调用（触发条件）

**以下情况必须调用本 Skill：**

1. **发布新版本** — 修改了功能/样式/内容，需要更新版本号时
2. **更新文档** — 修改 CHANGELOG、AGENT_HANDOFF、工作台搭建总结等文档时
3. **Git 提交前** — 任何代码/文档/资源准备提交前，检查提交时机和信息格式
4. **不确定能不能提交时** — 拿不准是否该提交、怎么提交时

## 一、文档职责分工（7 份）

| 文档 | 职责 | 读者 | 更新时机 |
|---|---|---|---|
| **项目约束总览.md** | 约束规则的**索引入口** + 新增/修改文件**唯一检查清单** | Agent | 新增约束类型/检查项时 |
| **文件约束隐患与规避方案.md** | 约束风险记录 + 规避方案（软约束怎么变硬） | Agent | 发现新隐患/落实规避方案时 |
| **AGENT_HANDOFF.md** | Agent 交接上下文（项目状态+设计原则+经验教训+目录结构） | 新 Agent | 每次版本变更、有经验教训沉淀时 |
| **CHANGELOG.md** | 版本更新日志（文件级变更，方便回溯） | Agent + 用户 | 每次版本发布时 |
| **工作台搭建总结.md** | 问题跟踪 + 版本更新简介（演进过程） | 用户 + Agent | 阶段性总结时（大版本后） |
| **文件说明.md** | 项目文件清单 + 每个文件干什么用 | 用户 + Agent | 新增/删除根目录文件或重要交付物时 |
| **用户偏好与AI协作建议.md** | 用户偏好档案 + 协作建议（设计偏好/工作习惯/沟通方式） | 新 Agent | 发现新偏好/协作模式变化时 |

### 同步规则

**不是所有文档每次都更，谁的职责范围内变了就更谁。**

| 同步场景 | 哪些文档必须更新 |
|---|---|
| 发新版本（版本号变化） | CHANGELOG ↔ AGENT_HANDOFF ↔ 工作台搭建总结（3份版本号必须一致） |
| 修改了已纳入版本控制的文件 | CHANGELOG（文件级变更记录）+ AGENT_HANDOFF（功能级摘要） |
| 新增/修改约束规则 | 项目约束总览（索引）+ 对应权威文档（详情） |
| 新增/删除根目录文件或重要交付物 | 文件说明.md |
| 踩坑/有经验教训 | AGENT_HANDOFF（协作改进章节）+ 文件约束隐患（如果是约束类） |
| 新的用户偏好/设计原则 | AGENT_HANDOFF（设计原则）+ 用户偏好档案 |

## 二、提交时机与验收流程

### 什么时候提交

| 提交时机 | 说明 |
|---|---|
| 完成一个独立功能 | 如"新增折叠卡片组件"、"修复筛选功能" |
| 完成一个 Bug 修复 | 如"修复颜色标签不显示" |
| 完成文档更新 | 如"更新CHANGELOG v2.20.0" |
| 完成一次重构 | 如"抽离公共模板" |
| 新增文件/资源 | 如"新增番茄钟页面" |
| 暂停工作/切换任务前 | 保存当前进度 |

**原则：小步快跑，一个功能一个 commit。不要攒一大堆才提交。**

### 验收流程（核心规则）

```
我做完 → 自检 → 给你验收 → 你说"可以提交" → 我才提交
```

**给你验收时我必须明确问："可以提交吗？"**，不能含糊。

**你回复"可以提交"、"提交吧"、"OK"等确认后，我才能执行 git commit。**

### 提交信息格式

格式：`<type>: <描述> [验收通过]`

type 可选值：
- `feat` — 新功能
- `fix` — Bug 修复
- `docs` — 文档更新
- `style` — 样式调整
- `refactor` — 重构（不改功能）
- `perf` — 性能优化
- `test` — 测试相关
- `chore` — 杂项/构建工具

示例：
- `feat: 新增章节精讲折叠卡片功能 [验收通过]`
- `fix: 修复知识点颜色标签不显示 [验收通过]`
- `docs: 更新CHANGELOG v2.20.0 [验收通过]`

## 三、破坏性操作界定

**破坏性操作 = 执行后可能导致未提交的工作丢失，且无法轻易恢复的操作。**

### 绝对禁止（红线）

| 操作 | 破坏性 | 原因 |
|---|---|---|
| `git reset --hard` | 极高 | 直接丢弃所有未提交变更，无法恢复 |
| `git checkout .` | 高 | 丢弃所有工作区修改 |
| `git clean -f` / `-fd` | 极高 | 删除未追踪文件/文件夹，无法恢复 |
| `git push --force` | 高 | 覆盖远程历史 |
| `rm -rf` 重要目录 | 极高 | 直接删文件 |

### 谨慎操作

| 操作 | 说明 |
|---|---|
| `git rebase` | 重写历史，冲突处理不好可能丢代码 |
| `git stash drop` | 丢弃暂存的代码 |
| 覆写文件前不备份 | 可能覆盖重要内容 |

### 安全操作（放心用）

| 操作 | 说明 |
|---|---|
| `git add .` | 只是暂存 |
| `git commit` | 只是提交 |
| `git revert` | 新增反向提交，历史保留 |
| `git diff` / `git log` | 只是查看 |
| `git stash`（暂存） | 代码还在 stash 里 |

**判断口诀**：如果这个命令执行后，未提交的代码或文件可能消失且 git 找不回来，就是破坏性操作。

## 四、版本发布检查清单

每次发新版本时，按以下清单逐项确认：

- [ ] CHANGELOG.md 已更新，包含本次所有修改文件
- [ ] AGENT_HANDOFF.md 版本号已同步更新
- [ ] 工作台搭建总结.md 版本号已同步（大版本才更，小版本可选）
- [ ] 版本号规则：语义化 MAJOR.MINOR.PATCH
- [ ] build.py 运行通过
- [ ] 浏览器验证通过（工作台完整路径）
- [ ] 已给用户验收，用户说"可以提交"
- [ ] 提交信息包含 `[验收通过]` 标记
- [ ] Git 提交成功
