# 先讨论再制作

本技能强制执行一条规则：**在方案经过讨论并得到用户确认之前，不得生成任何文件产物**。

## 何时触发

当用户要求以下操作时，必须触发本技能：

- 创建新的 HTML 页面、报告、文档、演示文稿或图片
- 生成文件类交付物（DOCX、PDF、PPTX、XLSX 等）
- 构建将保存为文件的新模块、仪表盘或可视化组件
- 任何会导致直接调用 `Write`、`html-report`、`docx`、`pptx`、`pdf`、`GenerateImage` 或类似产物生成工具的请求

## 特别提醒：交接文档任务

**从 AGENT_HANDOFF.md 或其他交接文档接收的任务，不代表已获得结构变更的确认。**

交接文档中的"下一步目标"仅说明工作方向，不等于用户已批准具体方案。如果任务涉及以下任一情况，仍必须先讨论再动手：

- 新增、删除或重组模块/分类/子项
- 改变现有页面的布局或信息架构
- 将原有内容从一个位置移动到另一个位置
- 用新结构替换原有结构（即使原文是"占位"）

**判断标准**：如果改动只影响"内容填充"（往已有结构里填数据），可以直接执行；如果改动影响"结构本身"（增删改分类、层级、导航项），必须先讨论。

## 工作流程

1. **停下来，不要急着创建**
   - 不要调用 `Write`、`html-report`、`docx`、`pptx`、`pdf`、`GenerateImage` 或任何产物生成工具。
   - 不要提前创建目录、脚手架或占位文件。

2. **澄清意图**
   - 确认目标、受众和主要用途。
   - 询问交付物应该帮助用户决策什么、追踪什么或传达什么。
   - 区分必须有内容和可选内容。

3. **提出 1–3 个可行方案**
   - 每个方案简要说明：结构、布局/风格方向、关键章节、取舍点。
   - 如相关，说明用户需要提供什么（文本、数据、图片、凭证）。
   - 方案要足够具体以便比较，但不要写出实际产物。

4. **等待用户确认**
   - 只有在用户选定方案、提出修改或明确说"就按这个做"／"开始生成"／"Proceed" 后才进入实施。
   - 如果用户态度模糊（"你定吧"／"随便"），选择最合理的方案，明确说明选择理由，然后请求最终确认。

5. **确认后**
   - 选择适当的工具或技能来生成确认的交付物。
   - 遵循现有项目规范（文件路由、命名、设计 token 等）。
   - 报告创建了什么以及保存在哪里。

## 例外情况

- **用户明确要求立即生成**：用户说"直接生成"／"不用讨论"／"just create it"，跳过讨论直接执行。
- **简单的一行文件**：创建单行配置或极小脚本不需要完整规划流程，但仍建议快速说一句"我将创建 X，可以吗？"
- **修复与编辑**：修改用户刚提到的现有文件不需要重新规划，**除非改动较大或重新设计了产物结构**。结构性改动（增删分类、重组导航、改变信息架构）不属于"修复与编辑"，必须走讨论流程。

## 语气

- 简洁。方案应可快速浏览。
- 使用用户的语言（本项目为中文）。
- 不要为暂停而过度道歉；将其表述为"确保产出符合预期"。
